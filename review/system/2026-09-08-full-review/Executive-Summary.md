# Executive summary

Running the full stack together and driving it from a real browser surfaced one real bug that none of the three isolated per-service reviews could have caught, because it only exists in the seam between two services: the AI service's match-explanation generator (`explanation_service.py`) returns negative-toned statements (e.g. "shows low contextual relevance to the role") in the same flat list as positive ones, and the frontend renders that entire list verbatim under a hardcoded "What supports this match" heading with no filtering. Reproduced live: a candidate who scored 0.87 overall (strong on skills, experience, and education, weak only on semantic relevance) had "shows low contextual relevance to the role" presented to the recruiter as one of the reasons *supporting* the match. This directly undermines the evidence-first review design the frontend redesign was built around.

A second, lower-stakes finding: the repository root's documented `npm run dev` / `npm run ai` command is broken — it points `uvicorn` at a module (`main:app`) that does not exist; the correct path (`app.main:app`) is only recorded correctly in `ai-service/railway.toml`. Any new contributor following the root `package.json` as documented would find the AI service silently never starts.

One positive result: the backend review had flagged that cross-site refresh-cookie behavior (`SameSite=None`, `Secure=true`) needed real-browser validation before launch. That validation happened here — after fixing the local CORS/Mongo misconfigurations described in Methodology, sign-in, session persistence across multiple page navigations, stage-advance, and sign-out all worked correctly over plain `http://localhost` in a Chromium-family browser, which treats `localhost` as a secure-context exception. This resolves the *local* half of that open question; the backend review's recommendation to test the real public origin in Chrome, Safari, and Firefox before launch still stands unchanged.
